# Daily PM Research Update: 2026-10-03

## The Short Version

Teresa Torres shows what it actually takes to make AI-generated opportunity solution trees trustworthy (evals and repair loops, not just a slicker prompt), LangChain publishes a real cost number for model routing in production agents (64% cost cut, no quality drop), and Notion keeps shipping the infrastructure layer for agents (skills libraries, shared memory) that most teams are still trying to bolt on themselves.

### Teresa Torres / Vistaly - Generating Opportunity Solution Trees With AI: Interview Synthesis, Evals, and Repair Loops
**Source:** https://www.producttalk.org/generating-opportunity-solution-trees-with-ai-how-vistaly-rebuilt-its-product-around-interview-synthesis-evals-and-repair-loops/
**Credibility:** High (direct case study from Teresa Torres, the originator of the opportunity solution tree framework, documenting a real product rebuild)

**What happened:** Vistaly rebuilt its product around AI-generated opportunity solution trees, using interview synthesis to automatically populate trees from raw customer conversations. Torres walks through how the team had to build evals and "repair loops" (mechanisms to catch and correct bad AI output) to make the auto-generated trees trustworthy enough for PMs to actually use in discovery work, rather than something that looks plausible but quietly misleads.

**Key patterns:**
- Interview synthesis: raw interview transcripts get processed into structured opportunities and needs that populate the tree automatically, instead of a PM manually tagging and categorizing
- Evals built specifically for discovery artifacts, not generic LLM output quality, meaning the test suite checks whether the extracted opportunities actually reflect what the customer said
- Repair loops: a feedback mechanism where mis-generated branches of the tree get flagged and corrected, which then presumably feeds back into improving future synthesis
- The rebuild wasn't a feature bolt-on. Torres describes it as rebuilding the product "around" this capability, meaning the core workflow shifted to assume AI-assisted synthesis as the default path

**Why it matters for PMs:** This is the most concrete example I've seen of what it actually takes to ship "AI does your discovery synthesis for you" without it becoming a trust liability. Everyone wants to automate interview synthesis. Almost nobody talks about the eval infrastructure required to make the output safe to act on. If you're building anything that summarizes or structures qualitative user research with AI, this is the blueprint: you need a way to systematically check if the AI got it right, and a loop to fix it when it didn't.

**Critical questions:**
- How much manual eval-writing and repair-loop-tuning did this take before the team trusted it enough to rebuild around it? That's the real cost of this approach, and it's not in the headline.
- Does the repair loop improve the model's future output, or is it just a one-time fix for a single tree? If it's the latter, this doesn't scale past a handful of customers.
- What's the failure mode when the eval misses something? Research synthesis errors are quiet (a wrong opportunity looks like a reasonable one), which makes them more dangerous than code bugs.

**Action you could take today:** If your team is using AI to synthesize user interviews or research notes, pull up your last three AI-generated summaries and manually check them against the raw transcripts. Count how many material errors you find. That number is your actual trust gap.

### LangChain - How to Build a Model Router in the Harness
**Source:** https://www.langchain.com/blog/how-to-build-a-model-router-in-the-harness
**Credibility:** High (first-party engineering writeup with a specific, measured production result)

**What happened:** LangChain built a model router into Open SWE's coding harness that automatically picks which model to use per task, and it cut median cost per coding task by 64% with no measurable drop in quality. They published how to build the same thing yourself.

**Key technical details:**
- The router sits inside the harness layer (the orchestration code around the agent), not inside the model call itself, meaning it decides which model to dispatch a given subtask to before execution
- Median cost per coding task dropped 64% with routing enabled
- No measurable quality regression reported, which is the claim that matters, since a cost cut that degrades output isn't actually a win
- This follows LangChain's broader run of harness-level work this quarter (trajectories, fine-tuning, custom apps), suggesting the harness itself is becoming the product surface, not just the model

**Why it matters for PMs:** Cost-per-task is becoming a real lever PMs can pull, the same way cloud infra teams optimize compute spend. If you're shipping an agent product and sending every task to your most expensive model by default, you're probably burning margin for no quality benefit. This is a concrete, measured example of the alternative: route cheap tasks to cheap models, expensive reasoning to expensive models, and let the harness make that call instead of hardcoding one model everywhere.

**Critical questions:**
- What's the routing logic actually keying off? Task complexity, token count, task type? The post promises a "how to build your own," so the real signal is in whether their heuristic generalizes outside coding tasks.
- "No measurable drop in quality" is doing a lot of work. What eval suite is this measured against, and does it cover the long tail of edge cases, or just the common path?
- Does this still hold as task complexity increases, or does the savings evaporate once you're routing genuinely hard problems that need the expensive model anyway?

**Action you could take today:** If you're running an agent or coding assistant in production on a single model tier, audit your last week of tasks by complexity and estimate what percentage could plausibly run on a cheaper model. That's your routing opportunity size before you build anything.

### Notion - A Skills Library for Every Agent
**Source:** https://www.notion.com/blog/a-skills-library-for-every-agent
**Credibility:** High (first-party product launch, authored by Geoffrey Litt)

**What happened:** Notion shipped a skills library that lets teams manage agent skills using Notion's existing editing, collaboration, and governance tools, then deploy those skills across different agents. This is the second infrastructure-for-agents piece Notion has shipped recently, following their shared memory system ("Lore") for AI agents.

**Key capabilities:**
- Skills are authored and versioned inside Notion using the same editing experience teams already use for docs, meaning no new tool to learn for the authoring side
- Collaboration and governance controls (presumably permissions, review, approval) apply to skills the same way they apply to any other Notion content
- Skills are built to be used "everywhere," implying they're meant to be portable across different agents and surfaces rather than locked into one Notion-native agent

**Why it matters for PMs:** Notion is building the boring-but-necessary layer that most teams are currently hacking together with scattered prompt files, READMEs, and tribal knowledge. If "skill" authoring and governance becomes a Notion-native workflow, that's a meaningful wedge, because it means the artifact that defines how your agents behave lives in the same tool your team already uses for docs and specs, with the same permissioning model. This is the same category-level move Wispr Flow made when it added team features: solo AI tool becomes team infrastructure.

**Critical questions:**
- How does versioning work when a skill changes and multiple agents are already using the old version? Is there a migration story or do agents silently pick up changes?
- What does "everywhere" actually mean technically? Is this MCP-based, or a Notion-specific format that requires an adapter for non-Notion agents?
- Governance for skills implies someone has to own approval. Who is that in practice, a PM, an eng lead, or whoever has Notion admin rights? That's an org design question dressed up as a product feature.

**Action you could take today:** List every place your team currently stores "how our agent should behave" instructions (Slack messages, README files, Notion docs, hardcoded prompts). If that list has more than two locations, you already have the problem this feature is solving.

## The Thread

**The agent "harness" layer is becoming the real product battleground, not the model.** LangChain's model router (64% cost cut via routing logic in the harness, not the model), Notion's skills library and shared memory system, and Cursor's recent Projects/Rollouts launches are all the same bet: once base model quality plateaus for a given task, the orchestration layer around the model, how it routes, remembers, governs, and recovers from errors, is where the actual product differentiation lives. Teresa Torres's repair-loop writeup is the discovery-tooling version of the exact same idea: the AI call is the easy part, the infrastructure that catches when it's wrong is the hard part and the actual product.
