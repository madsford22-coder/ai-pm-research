### Wispr Flow — Canto: Their First In-House Speech Model

**Source:** https://wisprflow.ai/canto
**Credibility:** High (first-party product announcement, shipped and live)

**What happened:** Wispr Flow shipped Canto, the first speech model they've built themselves. It's now live for all users with nothing to switch on. Before this, Flow was running on third-party speech models. Canto was explicitly trained on real-world audio — noisy environments, average microphones, non-studio conditions — rather than the clean-room audio that most speech models optimize for.

**Key capabilities:**

- Trains and tests on real-world audio (background noise, consumer-grade mics, accented speech), not lab-quality recordings
- Rolled out automatically to all existing users — no opt-in required
- First internal model asset, meaning Wispr Flow now controls its own transcription quality, latency, and cost curve going forward
- No explicit benchmarks published, but framed as solving a gap in existing models: poor performance in realistic use conditions

**Why it matters for PMs:** This is a classic vertical integration move. Wispr Flow was dependent on third-party speech models for the core function of their product. By building Canto, they now control the quality and cost of transcription directly — which means they can improve the product faster and stop paying the margin to an upstream provider. For any PM whose product depends on a third-party AI capability at the core of the experience, this is the playbook: once your volume justifies it and the differentiation is there, you build it yourself. The framing around real-world audio conditions is also a product signal — they clearly found that existing models (likely Whisper variants) failed users in non-ideal conditions, and that's what they went to fix.

**Critical questions:**

- What's the actual WER (word error rate) improvement in real-world conditions vs. what they were using before? The announcement doesn't say.
- At what user scale does building your own speech model make economic sense vs. buying? Wispr has raised $81M — is this timing driven by scale, by differentiation need, or by both?
- Does owning the model layer create new possibilities for Wispr Flow (custom vocabulary, on-device inference, domain adaptation) or is it mostly a cost play?
- Will they publish Canto's benchmarks, or is this model staying proprietary?

**Action you could take today:** If you have a core AI capability in your product that's entirely dependent on one upstream provider, map out what you'd need to justify building or fine-tuning your own version. What's the volume threshold? What's the differentiation gap? Wispr's move is a useful forcing function for that conversation.

### GitHub Blog — Should You Read the Code, Is RAG Dead, and Did Skills Kill MCP?

**Source:** https://github.blog/ai-and-ml/should-you-read-the-code-is-rag-dead-and-did-skills-kill-mcp/
**Credibility:** Medium-High (GitHub's own engineering blog, internal expert perspective — not an independent benchmark)

**What happened:** GitHub published a post asking three sharp questions about where the AI developer tooling stack is heading. The framing is notable because GitHub is asking them about their own ecosystem: RAG, MCP, and Skills are all things they're shipping or competing with. The title alone is a signal about how fast the architectural assumptions of AI tooling are shifting.

**Key technical questions raised:**

- "Should you read the code?" — whether agents should be given raw source code as context or work through higher-level abstractions
- "Is RAG dead?" — whether retrieval-augmented generation is being replaced by longer context windows, agent memory, or new retrieval paradigms
- "Did Skills kill MCP?" — whether GitHub's own Skills abstraction (structured tool definitions for agents) makes MCP (Anthropic's Model Context Protocol) redundant or obsolete

**Why it matters for PMs:** Three weeks ago, MCP felt like the obvious standard for giving AI agents access to tools and context. Now GitHub is asking if their own product — Skills — has superseded it. This is the pace of change in AI tooling right now: standards get proposed, get shipped, and get questioned within the same quarter. For PMs building on top of AI infrastructure, this means you need to hold architectural decisions loosely. The question "is RAG dead?" is especially relevant — many teams have spent significant engineering cycles building RAG pipelines. If the answer is "yes, for certain use cases," that changes prioritization and resourcing immediately.

**Critical questions:**

- GitHub has a conflict of interest here — they ship Skills, so "did Skills kill MCP?" is a self-serving question. What does the independent developer community actually think?
- If RAG is being deprecated in certain use cases by longer context windows, what's the cost curve comparison? Context is still not free.
- What happens to teams that standardized on MCP if Skills becomes the dominant abstraction in GitHub Copilot?
- Is this post actually making a claim, or is it surfacing a question the market is debating? (Title suggests the latter — worth reading the actual take.)

**Action you could take today:** If your team has bet on MCP or RAG as a core architectural pattern, pull the GitHub post and run a 30-minute review: what's the actual claim, does it hold for your use case, and is there a hedge worth putting in place now?

She took the concept from idea to working code — a real PM-led development case study, not a hypothetical. This connects directly to her previous post on evals and experiment variants, which showed her running 16 experiment variants to fix a single customer complaint.

**Key patterns from the write-up:**

- The workflow went from concept to functional code — not a prototype, but something she's using

When she says she built something without engineers, it's not a "look how easy this is" post — it's evidence that the bar for PM-led development has shifted. If that pattern holds, PMs who can code (at least at the vibe-coding level) have a meaningful speed advantage in discovery and experimentation.

**Action you could take today:** Watch the first 10 minutes of the video. If she's walking through her actual workflow and tooling choices, that's the highest-signal part. Note specifically what AI tools she uses and what the handoff point is where she'd need engineering support.
