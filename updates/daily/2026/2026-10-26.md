# Daily PM Research Update: 2026-10-26

## The Short Version

OpenAI published real usage data on how 165 work activities break down across 100 countries while simultaneously shipping a computer-use model aimed at automating a chunk of those same activities, Notion rebuilt its AI pricing around a credit system that bundles model routing decisions away from users, and Cursor's new Agent SDK signals that "define an agent as a folder of code" is becoming the default packaging format for custom agents.

### OpenAI - ChatGPT's Expanding World of Work (plus GPT-6.1 Terra for computer use)
**Source:** https://openai.com/index/chatgpt-expanding-world-of-work and https://openai.com/index/introducing-gpt-6-1-terra
**Credibility:** High (first-party data release plus product launch, same day)

**What happened:** OpenAI published "ChatGPT Signals" data covering 165 distinct work activities across nearly 100 countries, showing how ChatGPT usage patterns differ by role, country, and task type, and how that usage has shifted over time. On the same day, OpenAI launched GPT-6.1 Terra, described as bringing "fast and capable computer use to everyone." The pairing isn't a coincidence: one post shows what knowledge workers currently do with ChatGPT, the other ships a model built to let the same workers hand off more of that work to an agent that operates a screen directly.

**Key technical details:**
- Signals data spans 165 work activities and nearly 100 countries, tracked over time rather than as a single snapshot
- GPT-6.1 Terra is positioned specifically around computer use (navigating UIs, clicking, typing) rather than general chat or coding
- Published alongside a separate case study on Codex Ultrafast cutting OpenAI's own internal incident investigation from hours to minutes
- Also published same day: a Fanatics case study showing a "Shop the Look" feature tested across ~30,000 MLB products drove 10% higher engagement

**Why it matters for PMs:** This is OpenAI doing something useful and rare: publishing behavioral data about what people actually do with their product, categorized by activity and geography, rather than just aggregate MAU numbers. If you're building anything adjacent to "AI at work," this dataset is worth digging into for where usage is concentrated versus where it's flat. The Terra launch is the more consequential signal though. Computer use models that are "fast enough for everyone" (not just research demos) are the precondition for agents that complete tasks across any software, not just ones with APIs. That's a direct threat to any product whose moat is "we have a UI that only humans can use."

**Critical questions:**
- Does the Signals data include retention or is it usage frequency only? Usage breadth across 165 activities doesn't tell you if any single activity is sticky.
- How much of Terra's "computer use" capability actually works reliably on messy, non-demo interfaces (internal tools, legacy software) versus clean consumer websites?
- The Fanatics 10% engagement lift was tested across 30,000 products. Is that a controlled A/B or a before/after comparison? The case study framing suggests test rigor but the methodology isn't in the summary.

**Action you could take today:** Pull the OpenAI Signals data and check if any of the 165 work activities map directly to a workflow in your product. If so, that's a credible external benchmark for how much AI usage to expect in that specific task category.

### Notion - Agents Rebuilt Around a Credit System and Model Routing
**Source:** https://www.notion.com/blog/notion-ai-more-for-less and https://www.notion.com/blog/inside-notions-upgraded-model-router-auto
**Credibility:** High (first-party product and engineering blog posts)

**What happened:** Notion rebuilt its AI pricing and infrastructure around a new credit system, long-running agents, and the ability to bring your own AI model. Co-founder Akshay Kotharii frames it as "more for less": faster, more efficient Notion AI through smarter model routing. A companion engineering post from Ghita Houir Alami details how Notion's upgraded model router ("Auto") uses pairwise comparisons and calibrated judging to measure model quality at scale, essentially building an internal evals system to decide which model handles which request.

**Key technical details:**
- New credit-based pricing system replaces (or sits alongside) previous Notion AI pricing
- "Auto" model router picks the model per-request using pairwise comparisons and calibrated judging, not a fixed assignment
- Bring-your-own-AI option lets customers plug in their own model/API key rather than relying solely on Notion-selected models
- Long-running agents are part of the same release, implying the credit system accounts for agent tasks that run longer than a single chat turn

**Why it matters for PMs:** This is the second major pricing/infrastructure shift from Notion in recent weeks (following the 160-app connector push), and it's a clean example of a company exposing model routing as a product decision rather than hiding it. Building an internal model quality evaluation system (pairwise + calibrated judging) to power a router is a non-trivial infra investment that most teams skip in favor of hardcoding one model. If you're deciding whether to let users pick models or route automatically, Notion's bet is "route automatically, but let power users bring their own" rather than "expose every model as a toggle."

**Critical questions:**
- How does the credit system handle cost unpredictability from long-running agents? Metered credits for agent tasks is a different pricing problem than metered credits for chat completions.
- What's the actual quality delta the "Auto" router produces versus just defaulting to the best available model? The post emphasizes the measurement system but not the resulting user-facing quality difference.
- Does bring-your-own-AI cannibalize Notion's AI revenue, or is it aimed at enterprise customers who were going to self-host anyway?

**Action you could take today:** If your product has any model-selection logic, audit whether it's hardcoded or routed. Notion just published a measurement framework (pairwise comparison + calibrated judging) you could adapt for evaluating model swaps in your own stack.

### Cursor - Agent SDK: Package an Agent as a Folder of Code
**Source:** https://cursor.com/changelog/agent-sdk
**Credibility:** High (official changelog, specific and shipped)

**What happened:** Cursor shipped an Agent SDK that lets developers define an agent as a folder of code, test it with evals, and deploy it either to Cursor's infrastructure or their own. The workflow is `npx @cursor/agent-sdk init ./my-bot` followed by `agent-sdk dev` to run the bot locally with a playground before deployment.

**Key technical details:**
- Agents are defined as a folder of code (not a config file or UI builder), making them version-controllable and testable like normal software
- Built-in evals are part of the SDK, not bolted on afterward
- Deployment target is flexible: Cursor's own infra or self-hosted
- Local dev workflow mirrors standard software development (init, dev server, playground) rather than a no-code builder pattern

**Why it matters for PMs:** This continues a pattern across Cursor's last few releases (Cloud Agent Canvases, Origin App Marketplace, Remote Control for local agents) of Cursor expanding from "AI editor" into "agent platform." Packaging an agent as a folder of code with built-in evals is a meaningful product decision: it treats agents as software artifacts subject to the same testing discipline as application code, rather than prompts you tweak until they seem to work. If you're evaluating agent frameworks (LangGraph, Mastra, custom), Cursor's SDK is now a contender specifically because of the evals-first framing baked into the dev loop.

**Critical questions:**
- How does the evals tooling compare to dedicated eval platforms like LangSmith? Is this "good enough" for most teams or a lighter-weight substitute?
- What's the actual deployment story for "your own infrastructure"? Containerized? Does it require Cursor's runtime dependencies?
- Does defining agents as code (versus a visual builder) raise the floor for who can build agents, narrowing the audience to developers who already use Cursor?

**Action you could take today:** If you're prototyping an internal agent, try `npx @cursor/agent-sdk init` and see how the built-in evals workflow compares to however you're currently testing agent behavior (manual spot checks vs. automated evals).

## The Thread

**Agents are being productized as software artifacts, not prompts.** Cursor's Agent SDK (folder of code + evals), Notion's model router (pairwise comparison + calibrated judging as formal infrastructure), and AWS's prompt caching guide for agent context all point the same direction: the industry is moving past "write a good system prompt" toward treating agent behavior as something you build, test, version, and optimize for cost like any other production software component. That's a different skill set than most PM teams have staffed for.

## Sit With This

Notion built an internal model-quality measurement system (pairwise comparisons, calibrated judging) just to power automatic model routing, rather than exposing model choice as a user-facing setting. Cursor went the other direction by making agent evals part of the default developer workflow, putting the testing burden on whoever builds the agent.

**For your product:** If you're routing between AI models or providers, who owns the decision of which model to use for a given request, your infra team via an internal eval system, or the end user via a visible toggle? What would it take to find out if your current choice is actually the right one?
