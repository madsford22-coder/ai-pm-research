### LangChain - Can Jev Be a Better Agent Evaluator?
**Source:** https://www.langchain.com/blog/jev-agent-evals-langsmith
**Credibility:** High (first-party blog post, benchmark results from LangSmith team with methodology described)

**What happened:** LangChain ran a head-to-head test comparing Jev — TypeSafe AI's "System One" model designed for fast, structured decisions — against traditional LLM-as-judge approaches for agent evaluation. They measured accuracy, repeatability, latency, and cost. The framing is honest: this isn't a puff piece, they're asking whether Jev actually earns a spot in the eval loop or whether it's just cheaper and faster at the expense of correctness.

**Key technical details:**
- Jev is a System One model — designed for low-latency, structured outputs, not deep reasoning. It makes quick yes/no or categorical judgments rather than generating long chains of thought.
- The test ran Jev against LLM judges (the current standard in LangSmith evals) on agent trajectory evaluation tasks
- Key axes of comparison: accuracy (does it agree with human ground truth?), repeatability (does it give the same answer twice?), latency (how fast?), cost (how cheap?)
- The companion post explains how to wire Jev into a LangChain harness for agent evaluation pipelines

**Why it matters for PMs:**
Evaluation is the unglamorous thing that determines whether your agent actually ships. Most teams are still using LLM-as-judge, which is expensive, slow, and inconsistent enough that it bottlenecks iteration speed. If a System One model can handle the easy eval cases accurately and cheaply, you can reserve expensive LLM judges for edge cases — which changes the economics of running evals in CI. This also signals a broader pattern: just as we split "fast" and "slow" thinking in reasoning models, we may end up splitting eval infrastructure the same way.

**Critical questions:**
- Where does Jev fail? The post title asks "can it be a better evaluator" — if the answer is "sometimes," the categories of failure matter enormously for deciding when to trust it.
- How does repeatability compare to LLM judges in practice? LLM judges are notoriously inconsistent; if Jev is more deterministic, that alone might justify the tradeoff.
- What's the coverage story? A fast, cheap evaluator is only useful if it handles a meaningful fraction of the eval cases — what percentage requires escalation to a full LLM judge?
- Does this require TypeSafe AI as a dependency, or can the pattern be replicated with other structured-output models?

**Action you could take today:** If your team is running agent evals and iteration is slow because eval costs are high, pull up the companion post (https://www.langchain.com/blog/building-a-harness-with-jev) and map your current eval cases to categories: which ones require complex reasoning, and which are straightforward pass/fail judgments that a System One model could handle?

### Notion - Building Shared Memory for AI Agents in Notion
**Source:** https://www.notion.com/blog/building-shared-memory-for-ai-agents-in-notion
**Credibility:** High (first-party engineering blog, written by Hesham Salman from Notion's engineering team)

**What happened:** Notion published a technical walkthrough of "Lore," their internal system for giving AI agents persistent shared memory. Lore takes conversations, decisions, tasks, and durable facts and converts them into Notion pages that future agents — and the humans working alongside them — can reference. This is the infrastructure layer underneath the Skills Library announcement from earlier this week.

**Key technical details:**
- Lore stores memory as actual Notion pages, which means it inherits Notion's existing permissions, search, collaboration, and governance model
- Memory categories include: conversations (what was discussed), decisions (what was resolved), tasks (what was delegated), and durable facts (things that stay true over time)
- The design assumes agents and humans share the same memory surface — the goal is joint legibility, not a separate agent-only data store
- This connects directly to the Skills Library feature (https://www.notion.com/blog/a-skills-library-for-every-agent), which manages what agents can do; Lore manages what agents remember

**Why it matters for PMs:**
The hard problem with agents isn't capability — it's continuity. An agent that forgets what it did last session isn't trusted with anything important. Notion's approach is interesting because it doesn't build a separate memory database; it stores memory in the same place humans already work. That makes memory inspectable, editable, and subject to the same governance controls as everything else. If this pattern works, it's a blueprint for how any collaboration tool could add agent memory without creating a shadow data layer no one can audit.

**Critical questions:**
- Who owns memory cleanup? Lore presumably accumulates a lot of low-value memory over time — what's the policy for expiration or pruning?
- How does Lore handle conflicting memories? If two agents write contradictory "durable facts," what resolves it?
- Is memory retrieval semantic (search by meaning) or structural (navigate like a Notion database)? The answer changes how useful it is at scale.
- What's the privacy model? If agents store decisions as Notion pages, who has access — just the workspace, or the AI models training on it?

**Action you could take today:** Sketch the memory architecture for one of your team's current AI features. What does it need to remember across sessions? Who needs to be able to read or edit that memory? Notion's Lore framing (conversations / decisions / tasks / durable facts) is a useful starting taxonomy for your own design.

### Lenny's Podcast - Peter Sellis on What Actually Makes a Great PM
**Source:** https://www.lennysnewsletter.com/p/90-minutes-of-unfiltered-product
**Credibility:** High (Lenny's Newsletter, Peter Sellis is VP of Product at Discord, previously led product at Snap)

**What happened:** Lenny published a 90-minute conversation with Peter Sellis, one of the more experienced consumer product leaders in the industry. The teaser description — "designing teams like terrorist organizations, riding your best people hard, and the three oxymorons of a truly great PM" — suggests this is less polished framework-sharing and more honest reflection. Sellis has seen consumer product at Snap and Discord scale, which gives him a different lens than most guests.

**Key craft patterns (based on available excerpt):**
- The "three oxymorons of a great PM" framing suggests Sellis is thinking about PM archetypes through contradictions — things that look like opposites but both have to be true simultaneously (e.g., strong opinions that are loosely held, confident but uncertain)
- "Riding your best people hard" is a specific management philosophy: invest disproportionately in your highest performers, not your struggling ones — controversial but common among operators who've scaled fast
- "Designing teams like terrorist organizations" likely refers to small, autonomous, high-trust cells with clear missions — a Bezos-style two-pizza team framing applied to product squads

**Why it matters for PMs:**
Most PM craft content comes from consultants or coaches. Sellis is an operator who shipped at scale at two of the most competitive consumer products of the last decade. When operators talk about what great PMs actually do (vs. what they're supposed to do), the specifics usually differ from the playbook. The "oxymorons" framing is worth sitting with — it's a useful way to identify where PM advice breaks down into false binaries.

**Critical questions:**
- The "ride your best people hard" philosophy sounds appealing but has real failure modes — what's Sellis's view on burnout and retention risk?
- How do the "terrorist organization" team design principles hold up when you need cross-functional coordination between cells?
- The episode is 90 minutes, which is long. What's the actual highest-signal 20 minutes for a PM who's not early in their career?

**Action you could take today:** Listen to the episode (or read the transcript if Lenny publishes one) with one specific question in mind: "What does Sellis think makes a PM great that I don't currently do?" That framing will help you extract the genuinely useful parts faster than listening for frameworks.

## The Thread

**Shared memory is becoming the infrastructure story for agents.** Notion's Lore system, last week's LangChain multi-agent context post, and OpenAI's Agents API are all solving the same problem from different angles: how do you give agents continuity without creating unauditable shadow data stores? Notion's answer — store memory as regular pages with existing permissions — is the most PM-legible approach so far. Worth watching whether that pattern spreads or whether the field lands on something purpose-built.

## Sit With This

Notion's Lore system stores agent memory as regular Notion pages, inheriting the workspace's existing permissions and governance. That's a deliberate architectural choice: memory is visible and editable by humans, not locked in a separate database.

**For your product:** If you're building or planning an agentic feature, who can read and edit the agent's memory? If the answer is "only the AI system," what happens when the agent acts on a memory that's wrong or outdated? Map out your memory governance model before you ship.
