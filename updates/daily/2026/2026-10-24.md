# Daily PM Research Update: 2026-10-24

## The Short Version

LangChain published a concrete playbook for keeping long-running agents useful as context piles up, Notion's engineering team (led by Ghita Houir Alami) revealed exactly how they measure model quality at scale with their new Auto router, and Dare Obasanjo's numbers on Meta Muse's adoption give us the clearest data point yet on whether consumers actually want agents doing things versus just chatting.

### LangChain - Context Engineering for Deep Agents: How to Remember Without Keeping Everything in Context
**Source:** https://www.langchain.com/blog/context-engineering-deep-agents-remember
**Credibility:** High (first-party technical writeup from the team building the Deep Agents harness, with specific implementation patterns)

**What happened:** LangChain published a detailed breakdown of how long-running agents degrade as their context window fills up, and the specific techniques their Deep Agents harness uses to prevent it: offloading, summarization, skills, and subagents. This follows a companion post from the day before on retrieval techniques for the same harness, suggesting LangChain is building out a full "context engineering" doctrine rather than a one-off feature.

**Key technical details:**
- **Offloading**: moving information out of the active context window into external storage that the agent can query back into context when needed, rather than keeping everything resident
- **Summarization**: compressing completed subtasks or conversation history into condensed representations instead of carrying the full transcript forward
- **Skills**: packaging reusable procedures/knowledge as callable units rather than re-deriving them from scratch each session (this connects to Anthropic's "Agent Skills" donation to the Agentic AI Foundation from earlier this week)
- **Subagents**: delegating bounded subtasks to separate agent instances with their own scoped context, so the parent agent's window doesn't absorb the subagent's working memory
- Published alongside a retrieval-focused companion post the previous day, framing this as a two-part system: get the right context in (retrieval), then manage it well over time (memory)

**Why it matters for PMs:**
If you're shipping any agent that runs longer than a single turn, "it gets dumber the longer it runs" is the failure mode you will hit, and most teams discover it in production rather than in design. This gives you a vocabulary and a set of concrete levers (offload vs. summarize vs. delegate) to diagnose which failure you're actually seeing before you reach for "just use a bigger context window," which is usually the wrong fix and the most expensive one.

**Critical questions:**
- At what point does summarization lose information the user actually needed later? Is there a way to measure "summarization regret" before a user complains?
- How do these four techniques trade off against latency? Offloading and retrieval both add round-trips that a chat-only agent doesn't pay.
- Is this specific to LangChain's harness, or are these patterns portable to agents built on other frameworks (Mastra, raw API calls)?

**Action you could take today:** If you have an agent in production that handles sessions longer than ~10 turns, pull a transcript where a user complained about degraded quality and map which of these four failure modes (stale context, lost summary, no skill reuse, no subagent delegation) actually caused it.

### Notion - Inside Notion's Upgraded Model Router, "Auto"
**Source:** https://www.notion.com/blog/inside-notions-upgraded-model-router-auto
**Credibility:** High (first-party engineering writeup, named author and role: Ghita Houir Alami, Engineering Manager)

**What happened:** Notion's engineering team published how they rebuilt "Auto," the model router that decides which underlying LLM handles a given Notion AI request. The core of the post is about measurement: pairwise comparisons and calibrated judging as the method for evaluating model quality at scale, rather than single-score benchmarks. This ships alongside Notion's broader "Agents, rebuilt to do more for less" relaunch (smarter routing, long-running agents, bring-your-own-AI, new credit system), which was covered in a previous update, but this piece is the engineering deep-dive on the measurement methodology specifically, which hasn't been covered yet.

**Key technical details:**
- Pairwise comparisons: instead of scoring each model output in isolation, the system compares two outputs head-to-head to determine relative quality, which tends to produce more reliable rankings than absolute scoring
- Calibrated judging: the judging model's scores are adjusted/calibrated so that a "7/10" means the same thing across different judges or contexts, addressing a known weakness in naive LLM-as-judge setups
- Used to route live traffic to the model that performs best for a given task type, as part of the "do more for less" cost/quality tradeoff Notion shipped this month

**Why it matters for PMs:**
Every team routing between models (and increasingly, every team will be) hits the same wall: how do you know model A is actually better than model B for your specific workload, not just on a public benchmark? Notion just showed their work on this, and it's a legitimate alternative to buying an eval platform. Led by a woman engineering manager at a company most PMs use daily, this is a rare instance of a company publishing the "how we measure quality" methodology, not just the "we shipped routing" headline.

**Critical questions:**
- How much engineering investment does a calibrated pairwise judging system require versus just using an off-the-shelf eval tool? Is this a "build if you're Notion scale" or "build regardless" decision?
- Does calibration drift over time as underlying models update? How often do they recalibrate?
- What's the actual cost savings from routing versus just defaulting to the cheapest model that clears a quality bar?

**Action you could take today:** If you're currently picking a single model for a feature based on a vibe check or a public leaderboard, set up even a lightweight pairwise comparison (10-20 real user prompts, two models, a human or LLM judge picking a winner) before your next model upgrade decision.

### Dare Obasanjo - Meta Muse Adoption Numbers: 10M+ Sign-ups, Shopping Leads Usage
**Source:** https://www.threads.com/@carnage4life
**Credibility:** Medium (secondhand commentary citing adoption figures, not a primary Meta disclosure, but Obasanjo has a strong track record of sourcing credible numbers)

**What happened:** Dare Obasanjo reported that Meta's Muse agent hit 10 million-plus sign-ups across the US and Canada in roughly six weeks, with 25% daily active users and shopping as the most popular use case, representing 25%+ of weekly active users. This is the first adoption data point we've seen for Muse since its launch coverage, and it directly tests the open question around whether users want agents to *do* things versus just chat.

**Why it matters for PMs:**
25% DAU/sign-up ratio for a six-week-old agent product is a strong number if accurate, and shopping beating every other use case tells you something concrete: people are comfortable letting an agent take action (not just advise) in a low-stakes, recoverable domain like shopping before they trust it with higher-stakes categories like finance or email. If you're building agent features and debating which use case to lead with, "transactional and recoverable" beats "advisory and open-ended" as a wedge.

**Critical questions:**
- Is 25% DAU good, mediocre, or inflated relative to comparable early-stage consumer AI products? We don't have a clean benchmark.
- "Shopping" as the top use case could mean browsing/research, not actual completed purchases. The distinction matters enormously for monetization.
- This is unverified secondhand data from a single source. Has Meta confirmed these numbers anywhere official?

**Action you could take today:** If your product has an agent feature, check whether your current top use case is transactional/recoverable or advisory/high-stakes, and consider whether leading with the former in onboarding would build trust faster.

## The Thread

**The industry is quietly standardizing on "context engineering" as the next discipline after prompt engineering.** This week alone: LangChain shipped two posts on memory and retrieval for long-running agents, Notion published its model-routing measurement methodology, Anthropic donated Agent Skills to a foundation, and Vercel detailed how agents safely touch production. The common theme: everyone building agents that persist across sessions is converging on the same four or five problems (memory, retrieval, routing, permissions, skills reuse) and racing to publish their solution as the reference implementation before a de facto standard locks in.
