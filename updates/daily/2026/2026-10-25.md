# Daily PM Research Update: 2026-10-25

## The Short Version

Harrison Chase laid out the five recurring components LangChain keeps rebuilding into every internal agent (Slack-native, per-tool identity, layered memory, sandboxed execution, schedule-driven), LangChain's own blog backed that up with two deep posts on context engineering for long-running agents, and Figma quietly shipped enterprise AI credit controls that tells you exactly who's actually footing the bill for all this agent experimentation.

### LangChain - The Five Components of a Company Agent Harness
**Source:** https://x.com/hwchase17 (X post/article, October 24, 2026)
**Credibility:** High (first-party, from LangChain's co-founder describing internal production patterns)

**What happened:** Harrison Chase published a breakdown of the recurring architecture LangChain keeps reusing across their internal company agents. Across multiple different agent use cases inside LangChain, five components show up every time: the agents live in Slack, they handle identity on a per-tool basis, they maintain both global and per-user memory, they execute code in a sandbox, and they largely run on schedules rather than waiting for a trigger.

**Key technical details:**
- Agents are distributed through Slack as the primary interface, not a standalone app or dashboard
- Identity/auth is handled per-tool, meaning each integration the agent touches (calendar, docs, CRM) has its own scoped credential rather than one global identity
- Memory is split into two tiers: global (shared context across all users of the agent) and per-user (personalized state)
- Code execution happens in a sandbox, separating agent reasoning from the blast radius of code it runs
- Most agents run on a schedule (cron-like) rather than purely reactive/on-demand triggers

**Why it matters for PMs:**
This is a rare "here's the actual reference architecture" post from a company building agent infrastructure for a living, and it lines up almost exactly with what LangChain's own blog has been publishing this week on context engineering (offloading, summarization, retrieval-first memory). If you're scoping an internal agent for your own team, this is a checklist: where does it live, how does it handle per-tool auth, what's global vs. personal memory, where's the sandbox, and is it scheduled or reactive. The Slack-as-interface and schedule-over-trigger choices in particular cut against the "agent as chatbot" default most teams reach for first.

**Critical questions:**
- Does "per-tool identity" scale cleanly once an agent touches dozens of tools, or does credential sprawl become its own maintenance burden?
- What's the actual boundary between global and per-user memory in practice, and what happens when they conflict?
- Is "runs on a schedule" a scalability choice or a trust choice (less autonomy, more predictability)?

**Action you could take today:**
Map your own internal agent prototypes against these five axes (interface, identity, memory tiers, execution sandboxing, trigger model) and flag the ones you've skipped entirely.

### LangChain - Context Engineering for Long-Running Agents: Two-Part Deep Dive
**Source:** https://www.langchain.com/blog/context-engineering-deep-agents-remember and https://www.langchain.com/blog/context-engineering-starts-with-retrieval
**Credibility:** High (first-party engineering content from the team building the Deep Agents harness)

**What happened:** LangChain published two companion posts this week on how their Deep Agents harness keeps long-running agents from degrading as context piles up. The first covers offloading, summarization, skills, subagents, and memory as mechanisms to keep the active context window focused. The second argues that effective context engineering starts with retrieval, not storage, because agents waste time and tokens on clumsy searches, oversized results, and stale data.

**Key technical details:**
- Offloading: moving information out of the active context window into external stores that can be pulled back in on demand
- Summarization: compressing accumulated history instead of keeping it verbatim
- Skills and subagents: delegating specific chunks of work to narrower agents so the parent context doesn't balloon
- Retrieval-first design: the claim is that most context bloat comes from bad retrieval (oversized, stale, or poorly targeted results), not from a lack of summarization downstream

**Why it matters for PMs:**
If you're building or buying any agent product meant to run for more than a single turn (a research agent, a support agent, an ongoing project assistant), context degradation is the silent failure mode that shows up as "it got worse the longer I used it." This is the first concrete, named pattern language for that problem from a team that ships agent infrastructure at scale, and it's a useful vocabulary to bring into a build-vs-buy conversation with your own ML/infra team: are we offloading, summarizing, or just hoping the context window is big enough?

**Critical questions:**
- How do you measure "context degradation" in a product metric, before users start complaining?
- At what point does the overhead of a retrieval + summarization pipeline outweigh just using a bigger context window?
- Does this pattern hold for consumer-facing agents, or is it mainly a problem for developer/enterprise agent harnesses?

**Action you could take today:**
If you have a long-running agent feature in production, pull a sample of sessions longer than 20 turns and check whether response quality degrades over the session. That's your baseline for whether this problem is actually costing you anything.

### Figma - New Enterprise AI Credit Controls for Admins
**Source:** https://help.figma.com/hc/en-us/articles/41944442159767-Set-AI-credit-limits (October 22, 2026)
**Credibility:** High (first-party changelog/release notes)

**What happened:** Figma shipped new admin controls for Enterprise plans that let admins set and manage paid AI credit limits, alongside other collaboration and automation controls. This follows Figma's broader rollout this month of Gemini 4 Argon in Figma Make and the Figma agent going GA.

**Key capabilities:**
- Admins on Enterprise plans can now set AI credit limits across their org
- Paired with broader "team collaboration" and "everyday task automation" controls in the same release
- Comes two weeks after Figma Make exited beta with multi-model support (you can pick which AI model powers your prototype)

**Why it matters for PMs:**
This is the unglamorous but necessary other half of every AI feature launch: once an org rolls out AI-powered tools to hundreds of designers, someone in finance wants a budget cap. Figma shipping credit limits right after shipping the Figma agent GA and multi-model Figma Make tells you adoption is real enough that cost control became urgent. If you're planning your own AI feature rollout to an enterprise customer base, this is the signal to build budget/credit controls into your admin console from day one rather than bolting it on after finance asks.

**Critical questions:**
- What happens to an in-progress agent task when an org hits its credit cap mid-run?
- Is credit consumption transparent enough for individual designers to self-manage, or does this create friction/surprise cutoffs?
- How does this interact with the "bring-your-own-AI" and multi-model options Figma just shipped, where cost varies by model choice?

**Action you could take today:**
If your product has any metered AI feature live with enterprise customers, check whether admins currently have any visibility into consumption before they hit a bill surprise. If not, that's a gap worth flagging this week.

**The agent-infrastructure conversation has shifted from "can it do the task" to "how do we run this safely and affordably at scale."** This week alone: LangChain published two posts on preventing context degradation in long-running agents, Chase described the reusable harness pattern (sandboxed execution, scoped identity, scheduled runs) LangChain uses internally, Vercel shipped a post specifically on how their own Agent accesses production safely, and Figma shipped credit limits for enterprise AI usage. ## Sit With This

LangChain's reference architecture puts agents in Slack by default, running on schedules rather than waiting for a user prompt. That's a deliberate choice to favor predictability and low-friction distribution over the "ask it anything, anytime" chat interface most teams default to first.
