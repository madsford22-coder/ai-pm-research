# Daily PM Research Update: 2026-09-11

## The Short Version

Three signals worth connecting today: Cursor just shipped Projects, which is the clearest bet yet that long-running agentic work is becoming a core IDE primitive. OpenAI dropped the Agents API the same day, giving any developer a managed harness for exactly that kind of work. And Pieter Levels, watching from the outside, noticed that regular people aren't vibe coding at all — they're just asking ChatGPT to do it. Those three things together say something important about who the real market is and what the infrastructure needs to support.

## Items

### Cursor — Projects: Long-Running Context for Larger Bodies of Work
**Source:** https://cursor.com/changelog/projects
**Credibility:** High (first-party changelog, shipped feature)

**What happened:** Cursor launched Projects on September 10, positioning it as the right abstraction for work that spans weeks or months — features, migrations, full apps. Projects maintains context persistently across sessions, can delegate to thousands of subagents simultaneously, and runs recurring work without requiring human intervention at each step. This is a meaningful architectural shift: Cursor is no longer just an AI-enhanced editor. It's becoming a platform for sustained, semi-autonomous software development.

**Key capabilities:**
- Persistent context over months of work, not just a single session
- Multi-subagent delegation for parallel task execution at scale
- Recurring work execution without per-loop human approval
- Builds on top of Cloud Agents and Origin (Cursor's own code hosting layer) from prior releases

**Why it matters for PMs:** The editor as a unit of work is being replaced by the project as a unit of work. That's a category redefinition, not a feature update. For PMs thinking about developer tools, the question shifts from "how good is the autocomplete?" to "how well does the system maintain intent and context over time?" This also raises the stakes for agent reliability — a bug in a single-session interaction is recoverable; a bug in a multi-week autonomous pipeline is not. The product surface area that needs to earn trust is getting much larger.

**Critical questions:**
- How does Cursor handle context drift over months? A project's goals and constraints evolve — does the system pick that up, or does it anchor to early context?
- At "thousands of subagents," what does cost management look like? Is there budget visibility before a run, not just after?
- What's the failure mode when a subagent chain goes wrong deep in a long-running task? Is recovery designed in, or is it abort-and-restart?
- How does this interact with the self-hosted machines feature from earlier this month for teams with data residency requirements?

**Action you could take today:** If you're evaluating Cursor for a team, run a real migration or feature project through Projects and specifically track where it loses context or makes incorrect assumptions after day 3. That's the fidelity test that matters, not day-one demos.

### OpenAI — Introducing the Agents API
**Source:** https://openai.com/index/introducing-the-agents-api
**Credibility:** High (first-party announcement, shipped product)

**What happened:** OpenAI launched the Agents API on September 10 — a managed service built on the Codex harness that handles orchestration, long-running sessions, and tool use. This is different from the Assistants API it partially replaces: it's explicitly designed for cloud-native, long-running agent workflows, not just multi-turn conversations. The same day, Vercel shipped native support for the Agents API on their platform, with a changelog entry titled "Build with OpenAI Agents API on Vercel."

**Key capabilities:**
- Managed orchestration layer — OpenAI handles the harness, not the developer
- Long-running session support (contrast: Assistants API was stateless across calls)
- Tool use built in at the API level
- Vercel integration available same-day, reducing time-to-deploy for web teams

**Why it matters for PMs:** OpenAI is making a direct play to be the infrastructure layer for agentic applications, not just the model provider. If you're building an AI product with complex multi-step workflows, you now have a genuine option to outsource orchestration to OpenAI and ship faster — but that choice comes with lock-in and opacity tradeoffs. The simultaneous Vercel integration is worth noting: it suggests a deliberate go-to-market push targeting the web developer segment that's already building on Vercel's AI SDK. This is platform strategy, not just API access.

**Critical questions:**
- What's the pricing model? "Managed service" often means costs that are opaque until you're in production.
- How does this interact with OpenAI's existing Assistants API? Is this a replacement, a successor, or a parallel track?
- For teams already using LangGraph or Mastra for orchestration, what's the migration story and what do they lose?
- What observability does the API surface? If the harness is managed, can you see what's actually happening inside a long-running run?

**Action you could take today:** If you have an existing agentic workflow that you built on LangChain or a custom harness, spend 30 minutes reading the Agents API docs and mapping your orchestration logic to what they offer. The question isn't "should I migrate" — it's "what would I give up and what would I get?"

### Pieter Levels — Normies Don't Vibe Code, They Just Ask ChatGPT
**Source:** https://levels.io/normies-dont-vibe-code
**Credibility:** Medium-High (first-hand observation from a prolific builder-on-AI; no methodology, but consistent with broader patterns)

**What happened:** Levels posted on September 10 that regular people — "normies" in his framing — aren't doing anything that looks like vibe coding. They're not using Cursor or Windsurf or even Lovable. They're opening ChatGPT, describing what they want, and asking it to do it. No IDE, no code editor, no workflow. The product they reach for is the one they already use for everything else.

**Why it matters for PMs:** This is the distribution insight that gets overlooked when we track developer tool launches. The vibe coding narrative is mostly about technical users who were already willing to engage with code — Cursor, Replit, Lovable are all still asking users to have *some* relationship with software. What Levels is pointing at is that the actual mass market is doing something simpler and more direct: task delegation through a chat interface they already trust. For PMs building AI products, this reframes the question. It's not "how do we make code generation accessible?" It's "how do we meet users where they already are?" That's a product surface that's already occupied — by ChatGPT.

**Critical questions:**
- If ChatGPT is the default interface for non-technical users doing "vibe coding," what does that mean for products trying to serve the same segment with a purpose-built tool?
- Is the behavior Levels describes durable, or is it a gap that gets filled when better consumer-facing builders (Lovable, etc.) reach mainstream distribution?
- What are users actually getting back from ChatGPT in these interactions — code they can't run, deployed apps, or something in between?

**Action you could take today:** Ask three non-technical people in your life how they'd build a simple app or automate a simple task right now. Don't suggest tools. Just listen to what they say first. Their answer is your product research.

### Marty Cagan — Strong Opinions, Loosely Held
**Source:** https://www.svpg.com/strong-opinions-loosely-held/
**Credibility:** High (first-party post from recognized PM thought leader)

**What happened:** Marty Cagan published a post today on the "strong opinions, loosely held" principle — examining how it applies (and sometimes gets misapplied) in product leadership contexts. The title is the principle; the post unpacks when it's a genuine signal of good product judgment versus when it becomes a cover for not committing or not doing the work to form a real opinion.

**Why it matters for PMs:** The "strong opinions, loosely held" framing is everywhere in product culture, but Cagan's critique is that it's frequently used to justify intellectual laziness — forming an opinion quickly (because you should "have opinions") without the rigor to know if it's actually warranted. In AI product development right now, this matters a lot. PMs are forming opinions about model capabilities, user behavior, and what to build — often based on very thin evidence. The distinction Cagan is drawing between genuine conviction-with-flexibility and opinion-as-performance is worth sitting with.

**Critical questions:**
- How do you distinguish between "I updated my view because I saw new evidence" and "I updated my view because someone pushed back"?
- When is a loosely held opinion actually just a hedge?

**Action you could take today:** Pick one opinion you've stated about your product or users in the last week. Write down the actual evidence behind it. If you can't fill a paragraph, the opinion was looser than you thought.

## The Thread

**The agentic infrastructure layer is consolidating fast.** This week alone: Cursor shipped persistent Projects, OpenAI launched a managed Agents API, Vercel integrated it same-day, and AWS dropped an evaluation metric specifically for multi-turn agents. These aren't separate product launches — they're pieces of an emerging stack. The question for PMs building on top of this stack is the same one that came up in every prior platform cycle: how much do you want to own, and how much do you want to rent? The "rent" option just got a lot more capable.
